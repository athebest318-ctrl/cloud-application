# Лабораторная работа № 8

## Постановка задач программного проекта

**Дисциплина:** Управление разработкой программного обеспечения облачных систем  
**Проект:** Cloud Application  
**Тема этапа:** Фильтрация и контроль состояния облачных сервисов

> Скриншоты в отчёте следует заменить изображениями из Swagger UI (`http://127.0.0.1:8000/docs`). Для каждого изображения приведена подпись и указано место вставки.

## Цель работы

Проанализировать требование заказчика, разложить его на функциональные требования и задачи разработки, определить зависимости и критерии приемки, а также реализовать фильтрацию облачных сервисов по состоянию.

## 1. Анализ требования заказчика

Исходное требование: пользователь должен получать список облачных сервисов с определённым состоянием. Приложение должно поддерживать состояния `running`, `maintenance` и `stopped` и не должно принимать произвольные значения.

| Вопрос | Ответ |
| --- | --- |
| Какую проблему необходимо решить? | Текущий API возвращал все сервисы и принимал любую строку в поле `status`. Пользователь не мог получить только сервисы нужного состояния. |
| Кто использует новую возможность? | Пользователь или клиентское приложение, которому нужен список сервисов определённого состояния. |
| Какие данные обрабатываются? | Идентификатор, название, тип и состояние сервиса. |
| Как изменяется API? | Добавляется необязательный query-параметр `status` для `GET /services`. |
| Какие возможности сохраняются? | Получение полного списка, создание, изменение, удаление сервисов и системные маршруты. |

**Цель этапа:** реализовать типизированные состояния сервисов и фильтрацию списка через API, сохранив совместимость с существующими CRUD-операциями.

## 2. Функциональные требования

| ID | Требование |
| --- | --- |
| REQ-01 | API должно поддерживать получение списка сервисов по состоянию. |
| REQ-02 | Поле `status` должно принимать только значения `running`, `maintenance`, `stopped`. |

## 5. Зависимости задач

```text
TASK-01 -> TASK-02 -> TASK-03 -> TASK-05
                  |       |
                  v       v
               TASK-04  TASK-06
                            |
                            v
                         TASK-08

TASK-03 -> TASK-07
TASK-03 -> TASK-09 -> TASK-10
```

TASK-03 нельзя полноценно завершить до TASK-02, поскольку маршрут должен использовать готовую бизнес-логику фильтрации. TASK-04 и TASK-05 можно выполнять параллельно после реализации TASK-03: проверка CRUD и обновление документации не изменяют одну и ту же логику. Высокий приоритет сам по себе не отменяет технические зависимости.

## 6. Acceptance Criteria

### TASK-01. Ограничение значений состояния

- Некорректное значение `status` отклоняется с HTTP 422.
- Допустимыми являются только `running`, `maintenance`, `stopped`.
- Ограничение используется и при создании, и при изменении сервиса.

### TASK-03. Фильтрация списка

- Параметр `status` является необязательным.
- `GET /services` возвращает полный список.
- `GET /services?status=running` возвращает только сервисы со статусом `running`.
- Аналогично работают значения `maintenance` и `stopped`.
- Старый URL `/services` без параметров сохраняется.

### TASK-05. Документация

- Параметр `status` отображается в Swagger UI.
- В документации перечислены три допустимых значения.
- Приложение запускается и OpenAPI-схема формируется без ошибок.

### TASK-09. Самостоятельная задача

- Сортировка не изменяет исходный список сервисов.
- Поле сортировки и направление сортировки описаны в API.
- Запросы без сортировки продолжают работать.

## 7. Реализация

Для запуска приложения используется команда:

```text
uvicorn app.main:app --reload
```

После запуска документация доступна по адресу:

```text
http://127.0.0.1:8000/docs
```

Реализованные маршруты:

- `GET /services` — полный список сервисов;
- `GET /services?status=running` — фильтрация по состоянию;
- `POST /services` — создание сервиса;
- `PUT /services/{service_id}` — изменение сервиса;
- `DELETE /services/{service_id}` — удаление сервиса;
- `GET /status` — проверка состояния приложения;
- `GET /about` — информация о приложении;
- `GET /service-count` — количество сервисов.

## 9. Definition of Done

Задача считается выполненной, если:

- необходимые изменения реализованы в соответствующих модулях;
- приложение импортируется и запускается без ошибок;
- существующие CRUD-операции сохранены;
- фильтрация проверена для всех допустимых состояний;
- ошибочные значения отклоняются;
- OpenAPI-документация обновлена;
- результат соответствует Acceptance Criteria;
- план задач сохранён в `PROJECT_TASKS.md`.

## 10. Жизненный цикл задачи

| Состояние | Смысл |
| --- | --- |
| TODO | Задача сформулирована, но работа ещё не началась. |
| IN PROGRESS | Выполняется анализ или разработка. |
| REVIEW | Реализация готова и проходит проверку. |
| DONE | Все критерии приемки выполнены. |

## 11. Ответы на контрольные вопросы

1. **Требование и задача разработки:** требование описывает нужный результат для пользователя, а задача определяет конкретную работу команды для его получения.
2. **Декомпозиция:** разделение крупного требования на небольшие проверяемые задачи.
3. **Backlog:** упорядоченный список требований и задач проекта.
4. **Приоритет:** показывает важность и очередность задачи с точки зрения ценности и рисков.
5. **Зависимость:** ситуация, когда выполнение одной задачи невозможно или затруднено без другой.
6. **Acceptance Criteria:** конкретные условия, по которым принимается отдельная задача.
7. **Definition of Done:** общие условия готовности задачи или результата проекта, включая код, проверку и документацию.
8. **TODO:** задача ожидает начала работы.
9. **IN PROGRESS:** задача находится в разработке.
10. **REVIEW:** результат ожидает проверки.
11. **DONE:** критерии приемки выполнены, задача завершена.
12. **Почему нельзя планировать только по приоритету:** задача высокого приоритета может зависеть от другой задачи, которую необходимо выполнить раньше.
13. **Почему большие требования делят на задачи:** небольшие задачи проще оценивать, выполнять, проверять и принимать.
14. **Почему нужен проверяемый результат:** без него невозможно объективно определить, завершена ли работа.
15. **Отличие Acceptance Criteria от DoD:** Acceptance Criteria относятся к конкретной задаче, а DoD задаёт общий стандарт готовности для всех задач.
