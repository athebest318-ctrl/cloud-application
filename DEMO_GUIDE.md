# Демонстрация Cloud Application

## Для чего нужна программа

Cloud Application — учебный сервер управления облачными сервисами и файлами.
Программа показывает полный путь запроса: REST API принимает данные, проверяет
их, хранит сведения в PostgreSQL, сохраняет файлы в объектном хранилище и
разрешает операции в соответствии с ролью пользователя.

## Что умеет программа

- регистрировать пользователей и создавать сеансы после входа;
- передавать токен в заголовке `Authorization: Bearer`;
- показывать текущего пользователя через `GET /auth/me`;
- управлять облачными сервисами и их состояниями;
- загружать, скачивать и удалять файлы;
- назначать роли и проверять разрешения;
- возвращать `401`, когда пользователь не вошёл, и `403`, когда прав недостаточно;
- применять новую роль сразу, без повторного входа пользователя.

## Подготовка

Запустите проект из папки с `README.md`:

```powershell
.\run_windows.cmd
```

Откройте `https://localhost:8443/docs` при включённом HTTPS или
`http://127.0.0.1:8010/docs` при выключенном HTTPS. Для учебных пользователей используется
пароль `cloud12345`.

## Сценарий показа преподавателю

1. Выполните `GET /services` без авторизации. Покажите `401 Unauthorized` и
   объясните, что сервер не смог определить пользователя.
2. Выполните `POST /auth/login` для `student01`, скопируйте `access_token`,
   нажмите **Authorize** и вставьте токен.
3. Выполните `GET /auth/me`. Покажите пользователя `student01` и роль `viewer`.
4. Выполните `GET /services`. Запрос разрешён, потому что у `viewer` есть
   `services.read`.
5. Выполните `POST /services`. Получите `403 Forbidden`: пользователь известен,
   но у него нет `services.write`.
6. Выйдите из Swagger-авторизации, войдите как `student02` и вставьте новый
   токен. Повторите `POST /services`: роль `operator` имеет `services.write`,
   поэтому сервер вернёт `201 Created`.
7. Покажите, что `student02` получает `403` на `GET /access/roles`.
8. Войдите как `student03`. Покажите успешные `GET /access/roles` и
   `PUT /access/users/{id}/role`: администратор управляет ролями.
9. Назначьте `student01` роль `operator`, затем повторите запрос со старым токеном
   `student01`. Запись станет доступна без нового входа, потому что права каждый
   раз читаются из PostgreSQL.
10. Выполните `DELETE /auth/session/{token}` и повторите `GET /auth/me` с этим
    токеном. Ответ `401` показывает, что завершённый сеанс больше не даёт доступ.

## Короткое объяснение архитектуры

```text
Swagger или другой клиент
        ↓ Authorization Bearer token
FastAPI endpoint
        ↓ get_current_user
AuthSession → User → Role → Permission
        ↓ require_permission
PostgreSQL и объектное хранилище
```

Главная идея проекта: endpoint проверяет не название роли, а конкретное
разрешение. Поэтому новая роль, например `content_manager`, начинает работать
без изменения маршрутов, если ей назначены существующие permissions.
