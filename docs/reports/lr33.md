## Ответы на контрольные вопросы

1. **Что называется статическим анализом программного кода?** Проверка исходного кода без выполнения пользовательского сценария.

2. **Чем статический анализ отличается от отладки?** Статический анализ исследует текст и структуру, debugger исследует выполняющийся процесс.

3. **Требуется ли запуск приложения для ruff check?** Нет.

4. **Что называется linter?** Инструмент обнаружения нарушений правил и некоторых ошибок.

5. **Что называется formatter?** Инструмент унификации оформления кода.

6. **Чем linter отличается от formatter?** Linter диагностирует нарушения; formatter нормализует оформление.

7. **Для чего используется PEP 8?** Это рекомендации по стилю Python-кода.

8. **Почему проект может выбрать собственную длину строки?** Для согласованного оформления с учётом нужд команды.

9. **Для чего используется pyproject.toml?** Для хранения проектной конфигурации инструментов, в том числе Ruff.

10. **Почему Ruff не добавляется в runtime requirements.txt?** Он не нужен приложению во время обработки запросов.

11. **Для чего создан requirements-dev.txt?** Для воспроизводимой установки инструментов разработки.

12. **Что делает ruff check?** Проверяет код по выбранным lint-правилам.

13. **Что обозначает код F401?** Неиспользуемый импорт.

14. **Что обозначает F841?** Неиспользуемая локальная переменная.

15. **Для чего используется ruff rule?** Показывает назначение правила и примеры.

16. **Что проверяет E711?** Проверяет сравнения с None и рекомендует is или is not.

17. **Для чего применяется группа I?** Для проверки и сортировки импортов.

18. **Что означает F821?** Обращение к неопределённому имени.

19. **Может ли статический анализ обнаружить неопределённое имя до запуска?** Да, как показал эксперимент с undefined_status.

20. **Может ли Ruff гарантировать отсутствие логической ошибки?** Нет.

21. **Почему дефект ЛР №32 нельзя считать автоматически обнаруживаемым любым линтером?** range(1,max_attempts) синтаксически корректен; намерение разработчика не следует из текста автоматически.

22. **Что делает --statistics?** Группирует количество замечаний по кодам правил.

23. **Для чего используется --fix?** Применяет доступные безопасные исправления.

24. **Почему в основной работе не используется --unsafe-fixes?** Некоторые изменения способны повлиять на поведение и требуют отдельного решения.

25. **Почему после автоматического исправления необходимо выполнить git diff?** Нужно проверить область изменений и сохранение смысла.

26. **Что делает ruff format --check?** Проверяет соответствие formatter без записи изменений.

27. **Изменяет ли --check исходные файлы?** Нет.

28. **Для чего используется ruff format --diff?** Показывает предполагаемые изменения форматирования.

29. **Что делает ruff format без --check?** Применяет форматирование к файлам.

30. **Зачем formatter запускается после анализа?** Сначала устраняются проблемы правил, затем унифицируется оформление.

31. **Почему generated migrations исключены из основной проверки?** Чтобы не менять массово сгенерированную историю миграций без необходимости.

32. **Что называется quality gate?** Набор обязательных проверок перед принятием изменений.

33. **Почему check_quality.ps1 не должен автоматически изменять файлы?** Проверка должна оценивать состояние, а не скрыто переписывать проект.

34. **Для чего используется git diff --check?** Для поиска ошибок пробельных символов в Git diff.

35. **Почему после стандартизации выполняется smoke-проверка приложения?** Проверка стиля сама по себе не подтверждает работу API.

36. **Что называется регрессией?** Новый дефект в ранее работавшем сценарии.

37. **Почему чистый lint не заменяет функциональное тестирование?** Lint проверяет лишь выбранные свойства кода, а тесты проверяют поведение.

38. **Чем type checker отличается от formatter?** Type checker ищет несоответствия типов, formatter меняет оформление.

39. **Как журналирование, debugger и статический анализ дополняют друг друга?** Они показывают историю событий, состояние выполнения и нарушения в исходном коде соответственно.

## Вывод

Проект проходит lint и formatter; тесты и контейнерные запросы подтверждают сохранение рабочего поведения. Чистый lint сам по себе не доказывает отсутствие логических ошибок.
