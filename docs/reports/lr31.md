## Цель работы

Проверить JSON-журналы, уровни событий и сквозной request_id без раскрытия конфиденциальных данных.

## Подготовка и ход работы

Контекст запроса реализован через ContextVar. Middleware принимает допустимый X-Request-ID или создаёт новый, возвращает его клиенту и передаёт в исходящий запрос. Для lr31-success события обоих сервисов содержат один идентификатор. Вход с неверным паролем дал 401, недостаточное разрешение — 403. Прикладные журналы выводятся в stdout.

Схема: X-Request-ID → ContextVar → app → notification → JSON / stdout

## Анализ и результаты

DEBUG применяется к отдельным попыткам и разрешённым проверкам; INFO — к успешным запросам, входу и созданию уведомления; WARNING — к retry и отказам доступа; ERROR — к окончательным сбоям. CRITICAL в эксперименте не потребовался. Проверкой не обнаружены контрольный пароль, Bearer-токен, адрес получателя и текст уведомления. Middleware не пишет Authorization, query string и тело; вместо значения токена в URL сохраняется шаблон маршрута. Uvicorn access log отключён, httpx и httpcore ограничены WARNING.

## app / logging_config.py

```text
import json
import logging
import logging.config
from datetime import datetime, timezone

from app.request_context import get_request_id

EXTRA_FIELDS = (
    "service",
    "event",
    "method",
    "path",
    "status_code",
    "duration_ms",
    "user_id",
    "username",
    "permission",
    "target_service",
    "attempt",
    "error_type",
    "notification_id",
)


class JsonFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        payload = {
            "timestamp": datetime.fromtimestamp(
                record.created, timezone.utc
            ).isoformat(),
            "level": record.levelname,
            "logger": record.name,
            "message": record.getMessage(),
            "request_id": get_request_id(),
        }
        payload.update(
            {
                field: getattr(record, field)
                for field in EXTRA_FIELDS
                if getattr(record, field, None) is not None
            }
        )
        return json.dumps(payload, ensure_ascii=False)


def configure_logging(level: str) -> None:
    logging.config.dictConfig(
        {
            "version": 1,
            "disable_existing_loggers": False,
            "formatters": {"json": {"()": JsonFormatter}},
            "handlers": {
                "console": {
                    "class": "logging.StreamHandler",
                    "formatter": "json",
                    "stream": "ext://sys.stdout",
                }
            },
            "root": {"level": level.upper(), "handlers": ["console"]},
            "loggers": {
                "httpx": {"level": "WARNING"},
                "httpcore": {"level": "WARNING"},
                "uvicorn.access": {"handlers": [], "propagate": False},
            },
        }
    )

```

## app / middleware / request_logging.py

```text
import logging
import re
import time
from uuid import uuid4

from fastapi import FastAPI, Request

from app.request_context import request_id_var

logger = logging.getLogger(__name__)
VALID_ID = re.compile(r"[A-Za-z0-9._-]{1,64}\Z")


def register_request_logging(app: FastAPI, service_name: str) -> None:
    @app.middleware("http")
    async def request_logging(request: Request, call_next):
        supplied = request.headers.get("X-Request-ID", "")
        request_id = supplied if VALID_ID.fullmatch(supplied) else uuid4().hex
        token = request_id_var.set(request_id)
        started = time.perf_counter()
        try:
            response = await call_next(request)
            route = request.scope.get("route")
            logger.info(
                "HTTP request completed",
                extra={
                    "service": service_name,
                    "event": "http_request_completed",
                    "method": request.method,
                    "path": getattr(route, "path", "<unmatched>"),
                    "status_code": response.status_code,
                    "duration_ms": round((time.perf_counter() - started) * 1000, 2),
                },
            )
            response.headers["X-Request-ID"] = request_id
            return response
        except Exception as exc:
            route = request.scope.get("route")
            logger.error(
                "Unhandled request exception",
                extra={
                    "service": service_name,
                    "event": "http_request_failed",
                    "method": request.method,
                    "path": getattr(route, "path", "<unmatched>"),
                    "duration_ms": round((time.perf_counter() - started) * 1000, 2),
                    "error_type": type(exc).__name__,
                },
            )
            raise
        finally:
            request_id_var.reset(token)

```

## Ответы на контрольные вопросы

1. **Что называется журналированием приложения?** Запись событий работы приложения для диагностики и контроля.

2. **Чем журнал отличается от обычного print()?** Logging имеет уровни, обработчики, форматтеры и централизованную настройку.

3. **Какие стандартные уровни журналирования используются в Python?** DEBUG, INFO, WARNING, ERROR, CRITICAL.

4. **Для каких событий используется DEBUG?** Для подробностей попыток и разрешённых проверок доступа.

5. **Для каких событий используется INFO?** Для нормального завершения запросов, входа и создания уведомления.

6. **В какой ситуации применяется WARNING?** Для повторной попытки, ошибочного входа и отказа в разрешении.

7. **Когда следует использовать ERROR?** Для окончательной ошибки интеграции или необработанного сбоя.

8. **Каково назначение CRITICAL?** Для критического отказа, нарушающего работу всей системы.

9. **Почему в штатном режиме выбран уровень INFO?** Он показывает основные события без подробного потока отладки.

10. **Что делает logging.getLogger(__name__)?** Создаёт или получает logger с именем текущего модуля.

11. **Для чего используется Handler?** Отправляет записи в выбранный выходной канал.

12. **Для чего используется Formatter?** Преобразует запись в текст или JSON.

13. **Что такое структурированный журнал?** Журнал с заранее определёнными именованными полями.

14. **Почему для лабораторной работы выбран JSON?** JSON позволяет надёжно разбирать события программно.

15. **Какие поля содержит базовая запись журнала?** timestamp, level, logger, message, request_id; дополнительные безопасные поля по событию.

16. **Для чего используется request_id?** Связывает события одной операции.

17. **Почему одного timestamp недостаточно для удобной связи событий?** Одновременно могут выполняться несколько запросов с близким временем.

18. **Для чего применяется ContextVar?** Хранит идентификатор отдельно для текущего контекста выполнения.

19. **Как request_id попадает в Notification Service?** Клиент передаёт его в исходящем HTTP-запросе.

20. **Какой HTTP-заголовок используется для его передачи?** X-Request-ID.

21. **Почему middleware возвращает X-Request-ID клиенту?** Чтобы пользователь мог сообщить идентификатор проблемной операции.

22. **Почему журналируется request.url.path, но не полный URL с query string?** Query string может содержать секреты. В проекте дополнительно сохраняется шаблон маршрута, потому что токен встречается и внутри пути.

23. **Почему не журналируется тело HTTP-запроса автоматически?** Тело может содержать пароль, токен или персональные данные.

24. **Почему нельзя журналировать Bearer-токен?** Он позволяет действовать от имени пользователя.

25. **Почему нельзя журналировать пароль даже при ошибке аутентификации?** Пароль остаётся секретом независимо от результата входа.

26. **Какие сведения допустимо фиксировать при успешном входе?** Идентификатор пользователя, имя, результат и request_id без токена.

27. **Какой уровень используется для неправильного пароля?** WARNING.

28. **Какой уровень используется для отказа permission?** WARNING.

29. **Почему успешный permission можно фиксировать на уровне DEBUG?** Это частое штатное событие, полезное главным образом для отладки.

30. **Как журналируется retry?** Событием notification_request_retry уровня WARNING с номером попытки и типом ошибки.

31. **Какой уровень используется для окончательной недоступности сервиса?** ERROR.

32. **Какой уровень используется при timeout?** ERROR.

33. **Почему два сервиса должны использовать одинаковый request_id?** Чтобы можно было проследить одну операцию через границы контейнеров.

34. **Зачем журналировать duration_ms?** Для измерения задержки и поиска медленных операций.

35. **Почему прикладные логи контейнера направляются в stdout?** Docker собирает стандартные потоки без отдельного файла внутри контейнера.

36. **Как посмотреть логи app через Docker Compose?** docker compose logs app.

37. **Как посмотреть логи только notification?** docker compose logs notification.

38. **Что изменяется при LOG_LEVEL=DEBUG?** Добавляются DEBUG-события, например номера отдельных попыток.

39. **Требует ли изменение LOG_LEVEL изменения исходного кода?** Нет, достаточно изменить конфигурацию и пересоздать процесс при необходимости.

40. **Почему секреты не должны попадать даже в диагностический журнал?** Диагностические журналы часто сохраняются и доступны шире, чем секреты.

41. **В чём заключается принцип минимального журналирования данных?** Записывать только поля, необходимые для конкретной диагностической задачи.
