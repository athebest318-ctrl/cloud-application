## Цель работы

Проверить timeout, ограниченные повторные попытки и преобразование сетевых ошибок в ответы API.

## Подготовка и ход работы

Использован актуальный main проекта. Подготовлен образ cloud-application:0.8, который учитывает последующие изменения ЛР 34. Нормальный запрос возвращает 201 и accepted. После остановки Notification Service получен 503; при pause — 504. После восстановления вновь получен 201. Ошибочный upstream-ответ и преобразование в 502 проверены автоматическими тестами.

Схема: API → HTTPX / retry → Notification → 201 / 502 / 503 / 504

## Анализ и результаты

HTTPX ограничивает ожидание, интеграционный слой создаёт собственные исключения, router формирует публичный ответ. Базовая конфигурация: timeout=2.0, max_attempts=3, retry_delay=0.5. Паузы перед повторными запросами — 0.5 и 1.0 секунды. ConnectError и ConnectTimeout повторяются; ReadTimeout POST автоматически не повторяется, поскольку операция могла уже быть выполнена. Для более широких повторов нужен идемпотентный ключ и хранение результата. Settings дополнительно проверяет положительный timeout, минимум одну попытку и неотрицательную задержку.

## app / integrations / notification_client.py

```text
import asyncio
import logging
import time

import httpx

from app.config import settings
from app.request_context import get_request_id

logger = logging.getLogger(__name__)


class NotificationServiceError(Exception):
    pass


class NotificationServiceUnavailable(NotificationServiceError):
    pass


class NotificationServiceTimeout(NotificationServiceError):
    pass


class NotificationServiceBadResponse(NotificationServiceError):
    def __init__(self, status_code: int):
        self.status_code = status_code
        super().__init__(f"Notification service returned HTTP {status_code}")


async def send_notification(recipient: str, message: str) -> dict:
    url = f"{settings.notification_service_url.rstrip('/')}/notifications"
    payload = {"recipient": recipient, "message": message}
    timeout = httpx.Timeout(settings.notification_timeout_seconds)
    max_attempts = settings.notification_max_attempts

    fields = {"service": "cloud-application", "target_service": "notification"}
    logger.info(
        "Notification request started",
        extra={**fields, "event": "notification_request_started"},
    )
    for attempt in range(1, max_attempts + 1):
        logger.debug(
            "Notification request attempt",
            extra={
                **fields,
                "event": "notification_request_attempt",
                "attempt": attempt,
            },
        )
        started = time.perf_counter()
        try:
            async with httpx.AsyncClient(timeout=timeout) as client:
                response = await client.post(
                    url, json=payload, headers={"X-Request-ID": get_request_id()}
                )
                response.raise_for_status()
                logger.info(
                    "Notification request completed",
                    extra={
                        **fields,
                        "event": "notification_request_completed",
                        "attempt": attempt,
                        "status_code": response.status_code,
                        "duration_ms": round((time.perf_counter() - started) * 1000, 2),
                    },
                )
                return response.json()
        except (httpx.ConnectError, httpx.ConnectTimeout) as exc:
            if attempt == max_attempts:
                logger.error(
                    "Notification service unavailable",
                    extra={
                        **fields,
                        "event": "notification_service_unavailable",
                        "attempt": attempt,
                        "error_type": type(exc).__name__,
                    },
                )
                raise NotificationServiceUnavailable() from exc
            logger.warning(
                "Notification request retry",
                extra={
                    **fields,
                    "event": "notification_request_retry",
                    "attempt": attempt,
                    "error_type": type(exc).__name__,
                },
            )
            delay = settings.notification_retry_delay_seconds * (2 ** (attempt - 1))
            await asyncio.sleep(delay)
        except httpx.TimeoutException as exc:
            logger.error(
                "Notification service timeout",
                extra={
                    **fields,
                    "event": "notification_service_timeout",
                    "attempt": attempt,
                    "error_type": type(exc).__name__,
                },
            )
            raise NotificationServiceTimeout() from exc
        except httpx.HTTPStatusError as exc:
            logger.error(
                "Notification service returned error",
                extra={
                    **fields,
                    "event": "notification_service_bad_response",
                    "attempt": attempt,
                    "status_code": exc.response.status_code,
                    "error_type": type(exc).__name__,
                },
            )
            raise NotificationServiceBadResponse(exc.response.status_code) from exc
        except httpx.RequestError as exc:
            logger.error(
                "Notification service unavailable",
                extra={
                    **fields,
                    "event": "notification_service_unavailable",
                    "attempt": attempt,
                    "error_type": type(exc).__name__,
                },
            )
            raise NotificationServiceUnavailable() from exc

    raise NotificationServiceUnavailable()


async def get_notification(notification_id: int) -> dict:
    url = f"{settings.notification_service_url.rstrip('/')}/notifications/{notification_id}"
    async with httpx.AsyncClient() as client:
        response = await client.get(url)
    return response.json()

```

## Ответы на контрольные вопросы

1. **Почему удалённый HTTP-вызов менее предсказуем, чем локальный вызов функции?** Сеть, DNS и удалённый процесс могут отказать независимо от вызывающего кода.

2. **Что называется timeout?** Ограничение времени ожидания сетевой операции.

3. **Зачем ограничивать время сетевого ожидания?** Чтобы запрос не удерживал ресурсы неограниченно долго.

4. **Какие основные виды timeout различает HTTP-клиент?** Connect, read, write и pool timeout.

5. **Что представляет собой TimeoutException?** Общий класс HTTPX для исключений тайм-аута.

6. **Что означает ConnectError?** Не удалось установить соединение с удалённым сервисом.

7. **Что означает HTTPStatusError?** Получен HTTP-ответ, который raise_for_status считает ошибочным.

8. **Для чего используется response.raise_for_status()?** Проверяет HTTP-статус и поднимает HTTPStatusError.

9. **Что представляет собой retry?** Повтор операции после неудачи.

10. **Почему retry не должен быть бесконечным?** Бесконечные повторы задерживают ответ и создают дополнительную нагрузку.

11. **Что называется exponential backoff?** Экспоненциальное увеличение паузы между повторами.

12. **Какие задержки используются при базовом значении 0,5 с?** Перед вторым запросом 0,5 с, перед третьим 1,0 с.

13. **Сколько попыток используется в основной реализации ЛР №30?** Три попытки, включая первоначальный запрос.

14. **Почему повтор выполняется для ConnectError?** При ошибке установления соединения полезная операция обычно ещё не была передана серверу.

15. **Почему ReadTimeout не повторяется автоматически?** POST мог быть обработан до потери ответа; повтор способен создать дубликат.

16. **Чем POST отличается от безопасной операции чтения с точки зрения повторов?** POST обычно изменяет состояние, а безопасное чтение не должно создавать побочные эффекты.

17. **Что такое дублирование операции?** Одно пользовательское действие выполняется несколько раз.

18. **Как идемпотентность помогает при retry?** Повтор с тем же ключом возвращает прежний результат без повторного изменения состояния.

19. **Для чего созданы собственные исключения интеграционного слоя?** Скрывают детали HTTPX за понятными состояниями интеграции.

20. **Почему router не должен обрабатывать классы HTTPX напрямую?** Это сохраняет независимость HTTP-маршрута от выбранной клиентской библиотеки.

21. **В какой ситуации Cloud Application возвращает 503?** Когда соединение не установлено после допустимых попыток либо произошла иная ошибка доставки запроса.

22. **В какой ситуации возвращается 504?** При превышении времени ожидания ответа.

23. **В какой ситуации используется 502?** Когда зависимый сервис вернул ошибочный HTTP-статус.

24. **Почему внутренний ответ зависимого сервиса не обязательно передавать пользователю полностью?** Внутренний ответ может раскрыть детали инфраструктуры и не соответствует публичному контракту.

25. **Чем docker compose stop notification отличается от pause notification?** Stop завершает процесс, pause замораживает его без нормального завершения.

26. **Как восстановить paused-контейнер?** docker compose unpause notification.

27. **Почему после восстановления notification новый запрос снова может работать?** Новый запрос получает новое соединение с восстановленным сервисом.

28. **Где хранятся параметры timeout и retry?** В Settings; значения могут задаваться средой и Compose.

29. **Являются ли эти параметры секретами?** Нет, это обычные эксплуатационные параметры.

30. **Почему URL сервиса остаётся в конфигурации?** Адрес сервиса зависит от среды и не должен требовать правки кода.

31. **Зачем ограничивать число повторов?** Чтобы ограничить задержку и нагрузку при отказе.

32. **Почему пауза между повторными попытками увеличивается?** Это даёт зависимости время восстановиться.

33. **Почему автоматический retry может усилить перегрузку зависимого сервиса?** Множество клиентов одновременно создаёт поток повторных запросов.

34. **Для чего создан диагностический /test/error/{status_code}?** Для получения контролируемого ошибочного ответа при диагностике.

35. **Как проверить HTTPStatusError?** Вызвать тестовый маршрут и применить response.raise_for_status; автоматический тест проверяет исключение и преобразование в 502.

36. **Почему в этой ЛР не создаётся полноценная система логирования?** Полноценное журналирование относится к следующей ЛР 31.

37. **Что необходимо добавить для безопасного retry уже обработанного POST-запроса?** Идемпотентный контракт с устойчивым ключом операции и хранением результата на стороне сервиса.
