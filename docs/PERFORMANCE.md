# ЛР 34: воспроизводимая проверка производительности

Из корня проекта, используя Python с установленными зависимостями:

```powershell
python scripts/profile_service_report.py
python -m pytest -q
.\scripts\check_quality.ps1
python -m compileall -q app scripts
```

Исходный алгоритм сохранён в `scripts/service_report_baseline.py`, оптимизированный —
в `app/services/reporting.py`. Скрипт сохраняет каждый из пяти замеров, среднее,
минимум, SHA-256, параметры среды и ускорение в `evidence/lr34/measurements.json`.
Данные детерминированы формулой `(id * 37) % TYPE_COUNT + 1`.
Время генерации данных, проверки равенства и вычисления digest не входит в замеры.
Построение словаря входит. Для каждой пары размеров используются одни и те же данные.

Профили `profile_before.prof` и `profile_after.prof` создаются локально в
`evidence/lr34/` и исключены из Git. Текст pstats сохраняется рядом и включён в Git.
Профилируется один вызов компонента, а не генерация данных и сериализация.
Просмотр: `python -m pstats evidence/lr34/profile_before.prof`, затем
`sort cumulative`, `stats 20`, `quit`.

## Фактические результаты этого запуска

| Сервисы | Типы | Среднее до, с | Среднее после, с | Ускорение |
|---:|---:|---:|---:|---:|
| 5 000 | 200 | 0.028719 | 0.001450 | 19.81 |
| 20 000 | 200 | 0.112273 | 0.009281 | 12.10 |
| 50 000 | 200 | 0.272071 | 0.015717 | 17.31 |
| 20 000 | 20 | 0.015360 | 0.007064 | 2.17 |
| 20 000 | 1 000 | 0.480859 | 0.008787 | 54.73 |

Для основного случая уменьшение среднего времени — 91.73%.
Формулы: speedup = mean_before / mean_after;
reduction = (1 - mean_after / mean_before) * 100%.
Все digest совпали; дополнительно сравниваются сами списки.

Профиль исходной функции показывает около 0.100 с собственного времени
и 0.103 с вместе с вложенными вызовами. Это локализует затраты внутри
`build_service_report`, где для каждого сервиса выполняется линейный поиск.
Гипотеза: однократная индексация типов уберёт повторный проход по справочнику.
После замены cumtime составляет около 0.016 с.

`ncalls` — количество вызовов; `tottime` — собственное время функции;
`cumtime` — время вместе с вложенными вызовами. Встроенные сравнения внутри цикла
cProfile не считает отдельными вызовами: число вызовов не обязано уменьшаться.
При 20 000 / 200 исходный цикл делает 2 010 000 сравнений ID, новый вариант —
200 добавлений в индекс и 20 000 обращений `get`.

Вычислительная сложность меняется с O(N*M) на ожидаемую O(N+M).
Дополнительная память словаря — O(M). Для единичного поиска или совсем маленького
справочника его создание может не окупиться. Для больших справочников преимущество
растёт; по размеру списка сервисов ускорение не монотонно из-за разброса измерений.
Неизвестный тип остаётся `unknown`, порядок сохраняется. `setdefault` сохраняет
первое совпадение при повторяющихся ID, как в исходном алгоритме.

Дополнительный вариант `id → объект типа` также измеряется по пять раз.
Его результаты сохранены как `object_lookup`; один удачный запуск не доказывает
практически значимого преимущества. Это локальный эксперимент, а не оценка RPS,
SLA или производительности всей системы. Замеры зависят от фоновой нагрузки.

## Проверка действующего приложения

Образ: `cloud-application:0.7`. Для отдельного тестового развёртывания:

```powershell
docker build -t cloud-application:0.7 .
docker compose up -d
docker compose cp scripts app:/tmp/scripts
docker compose exec -T -e PYTHONPATH=/app:/tmp app python /tmp/scripts/verify_current_project.py --output /tmp/smoke.json
docker compose cp app:/tmp/smoke.json evidence/lr34/smoke.json
```

Сценарий создаёт учебные учётные записи student01–student04 с ролями, используя
`prepare_database` существующего сценария авторизации. Запускайте его на учебной
тестовой БД. Проверяются HTTP, PostgreSQL, миграции, Argon2, права, CRUD, файлы,
ограничение размера загрузки, уведомления и отзыв сессии.

Старые `verify_project.py` и `verify_access.py` отражают этапы до ЛР 21:
ожидают доступ к защищённым маршрутам без токена. Они не являются проверками
текущего API. Для текущей версии используйте новый сценарий и pytest.
Исправлено обнаруженное несоответствие: `/integration/notifications` теперь
возвращает 201 при успешном создании уведомления.

Успешные проверки приложения не подтверждают полноту старых отчётов и ответов
на вопросы всех лабораторных. Например, миграция 008 специально запрещает откат
хешей в открытые пароли; полный `downgrade base` не является допустимым сценарием.
